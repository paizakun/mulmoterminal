# perf: 命令履歴の読み込みを、毎回の全走査からレジュームに変える

issue: #1750

## きっかけ

#1749 の Prompts ペインは、claude の命令履歴（`~/.claude/history.jsonl`）を**毎回ファイル全体**
ストリーム走査している。末尾読みだと「1 ユーザー 1 ファイル」のため古いセッションが窓の外に
丸ごと落ちる（実測 254 セッションが 0 件表示）ので、正しさのために全走査を選んだ経緯がある。

オーナーから「読み込み速度は改善したい」（2026-08-16）。

現状の実測（この開発機）: **7.8 MB / 31,615 行、1 回の全走査が中央値 46ms**。増加は約 0.7 MB/月。
ペインが開いている間、命令を送るたびに（400ms デバウンスで）これが走る。

## issue の本命案（逆走査）は採らない — 実測で前提が崩れた

issue #1750 では「末尾から逆走査し、必要な件数が揃った時点で打ち切る」を本命としていた。
前提は「直近 101 件は末尾数百 KB に収まる」。**実測したら半分しか成立しない。**

開いている 14 セルについて、直近 101 件を集めるのに必要な末尾バイト数:

| | |
|---|---|
| 5 本（命令の多いセッション） | **122 KB 〜 798 KB** — 逆走査が大きく効く |
| **9 本** | **ファイル全体** — そもそも 101 件持っていない（14 件 / 50 件 / 1 件 …）ので、先頭まで読まないと「もう無い」と確定できない |

つまり逆走査は**命令の多いセッションの初回読みしか救わない**。若いセッション・作ったばかりの
セルでは全走査のままで、そこは一番よく開かれる。加えて、後方チャンク読みという新しい
インフラを 1 つ抱えることになる。

## 採る案: (anchor, offset) メモ ＋ レジューム

このファイルは **append-only** なので、前回止まった offset から続きだけ畳めばよい。

- **初回**: これまでどおり全走査（46ms）
- **2 回目以降**: 前回の offset から EOF まで ＝ **新しく書かれた数百バイトだけ**

逆走査と違い、**セッションの大小に関係なく効く**。しかも新しいインフラが要らない:
`server/infra/jsonl-file.ts` の **`forEachJsonlRecordIn(file, {from, to, atLineStart}, onRecord)`**
が、まさにこの用途（#1377 で transcript のフォールドを再開可能にしたときのもの）として既にあり、
「どこで止まったか」を返す。`transcript-fold.ts` が同じ形の (mtime, size) メモを使っている。

### メモの形

```ts
interface HistoryMemo {
  /** このメモがどの問いに対する答えか。変わったら作り直す。 */
  key: string;
  /** 前回の走査が止まった行頭 offset。ここから再開する。 */
  offset: number;
  /** その位置で「同じ中身」だったことの指紋（先頭 256B ＋ offset 直前 256B のハッシュ）。 */
  anchor: string;
  /** スライディング窓の状態そのもの（既存の ClaudePromptScan）。 */
  scan: ClaudePromptScan;
  /** この窓が最終的に乗っている「全走査」の時刻。resume は引き継ぐだけで押し直さない。 */
  fullScanAt: number;
}
```

**`key` が要る理由**: 同じセッションでも、読むべき id の集合と `/clear` の floor は変わりうる。

- `claudeSessionIds` がフックで学習して id が増える
- `/clear` が起きて floor（`clearedAtOf`）が付く

どちらもスライディング窓の中身を変えるので、`historyIdsFor(...)` と `since` から作った文字列を
key にして、変わったら offset 0 から作り直す。**古い答えを新しい問いに使い回さない。**

**`anchor` が要る理由**（レビューと CI で 4 回かけて判明。当初の計画には無かった）:
「前回の offset は今も同じファイルの同じ位置か」を確かめる必要がある。

**メタ情報で判定しようとして 3 回失敗した。**

1. `size` だけ → 削除され元より大きく育った別ファイルを「増えた」と誤認する
2. `inode`（＋ floor した `birthtime`）→ **CI（ubuntu）が実演**。inode は再利用され（200/200 一致）、
   同一ミリ秒の再作成も普通に起きる（173/200 衝突）。macOS は毎回新しい inode を返すので、
   ローカルでは決して再現しない
3. `inode` ＋ 全精度 `birthtime` → 削除・再作成は捉える（0/200）が、**in-place の書き直しは
   inode も birthtime も保存する**（Codex）。旧 offset を超えて再成長すると追記と区別できない

**メタ情報は「どのファイルか」を答え、レジュームが要るのは「何が入っているか」。** この差が
上の 3 つ全部の正体で、中身を見る以外に閉じ方が無い。

**両端を取る理由**（テストが暴いた）: このファイルは各行が
`…"project":"<dir>","sessionId":"<uuid>"}` で終わり、**1 セッションでは行が違ってもバイト単位で同一**。
末尾だけの窓は「中身」ではなく「書式」の指紋になり、まったく別のファイルと一致してしまう。
変わるのは行頭側の `display` で、置換なら先頭も変わる。

**証拠であって証明ではない**: offset までの全バイトが不変であることを証明するには読むしかなく、
それは resume が避けたいコストそのもの。両端が一致して中間だけ違うファイルは、append-only の
ログが自分で作る状態ではない。ハッシュにするのは、この中身がユーザーの命令文そのものだから。

**その限界を「無期限」から「有期限」にする**（Codex）: 両端の窓の外だけを書き換える改変は
anchor に見えない。閉じるには全バイトを読むしかないので、代わりに **memo が乗っている全走査の
年齢に 10 分の上限**（`MEMO_MAX_AGE_MS`）を付ける。年齢は memo ではなく**連鎖**に付く
（resume は `fullScanAt` を引き継ぎ、押し直さない）。押し直す実装だと 400ms ごとに読まれる
ペインでは永久に期限切れにならない。コストは 10 分に 1 回の 50ms。

**走査の全部を 1 つの handle から読む理由**（Codex → CodeRabbit で 2 段階）:

まず、fold と anchor 読みが**別々に open する**と、その間に差し替わったとき「旧ファイルの窓 ＋
新ファイルの anchor」が対で memo に入り、以降の読みすべてが汚染される（Codex）。先頭 256B の指紋を
走査の前後で比べる案を入れたが、**先頭を保った置換**は素通りする（CodeRabbit）。パスを読み直す限り、
外から見て原本と区別できないので、どんな指紋でも塞げない。

**パスではなく handle を「そのファイル」として扱う。** `plan` / `fold` / 保存する `anchor` が同じ
handle を通るので、走査中にパスがどう動いても互いに食い違わない。infra の range fold が handle を
受け取れる（`JsonlSource = string | FileHandle`）。

**handle からストリームを作らない**（実測）: `FileHandle.createReadStream()` は `destroy()` で
handle ごと閉じ、`autoClose: false` は効かない（node 24 で EBADF を確認。fd 経由でも同じ）。
`forEachCompleteLine` は `finally` で `destroy()` するので、そのままだと後続の位置指定読みが全滅する。
handle 側は位置指定読みでチャンクを供給する。

**それでも handle が答えないのは「同じ inode の中身が書き換わる」場合**（CodeRabbit）。そこで走査は
**畳む境界の前後を自分で読む**: resume なら memo の offset、初回走査なら走査開始時点の EOF に anchor を
取り、fold の後に同じ handle で取り直して一致を確かめる。初回走査は突き合わせる memo が無いので、
これが無いと「書き換え前の窓 ＋ 書き換え後の anchor」を保存してしまう。

**長さガードを別に持たない理由**: offset まで読めなければ anchor が `null` になり、それが
そのまま「作り直す」判断になる。当初は「走査前に stat した size」を持つ設計だったが、走査中の
追記で stream がその size を超えるため、両者の間への in-place truncate をすり抜けていた。

### 無効化

- **key が変わった** → 上記
- **anchor が一致しない** → その位置の中身が違う（差し替え・in-place 書き直し）
- **anchor が読めない（`null`）** → offset まで届かない（truncate / ローテート / 消えた）
- **畳む境界の anchor が走査の前後で違う** → 読んでいる最中に中身が書き換わった（初回走査を含む）
- **全走査から 10 分が経った** → anchor に見えない改変が残り続けないための上限
- **セッションが teardown された** → `lifecycle.ts` の reap で削除（`claudeSessionIds` と同じ扱い）

`mtime` は見ない（追記のたびに変わるので、同一性の判定に使えない）。

## codex の rollout はどうするか

**今回は触らない。** rollout は「1 会話 1 ファイル」で、このマシンの 2,586 本のうち 4MB 超は 3 本、
最大 5.9MB。同じメモ化は素直に載るが、

- 読む頻度が claude より低い（codex セルは相対的に少ない）
- ファイルが小さいので 1 回の走査が安い

ので、**効果と変更量が釣り合わない**。必要になったら同じ形で足せる（`resumePlan` はセッション
固有のものを何も持たない）。この判断は PR 本文に書く。

## 変更

**`server/session/prompt-history-memo.ts`（新規・純関数寄り）**

- `memoKeyFor(ids, since)` — 問いの同一性
- `resumePlan(memo, key, anchorNow, now)` — `{ from, reuse }` を返す純関数。
  「作り直す／続きから」の判断だけを持ち、fs には触らない。**ここがテストの主戦場**
- `anchorOf(head, tail)` — 位置の指紋。ハッシュにするのは、これがユーザーの命令文そのものだから

**`server/session/session-reads.ts`**

- `claudePrompts` が memo を引き、`forEachJsonlRecordIn(file, { from, atLineStart: true }, …)` で
  差分だけ畳む。初回は `from: 0`
- 走査後に memo を更新（offset は `forEachJsonlRecordIn` の戻り値）
- **resume した scan はコピーしてから畳む**（`copyClaudePromptScan`）。メモは共有物で、
  同一セッションの読みが重なると同じ配列に二重に畳み込まれるため

**`server/session/lifecycle.ts`** — teardown で memo を落とす

## テスト

- `resumePlan` の純関数テスト: 初回 / 続き / offset==size（新規なし）/ key が変わった /
  anchor が違う / anchor が読めない（`null`）/ offset 0 のメモ / 全走査が古すぎる
- `anchorOf` の純関数テスト: 1 バイト違いを両端それぞれで分離する / 行末の書式が同一でも分離する /
  指紋が中身そのものを持ち出さない
- 実ファイルを使う結合テスト: 履歴を書く → 読む → **追記** → 読む で、
  ① 2 回目が追記分だけを読むこと（offset が進む）② 結果が全走査と一致すること
- **全走査との等価性**: 同じ入力に対し「メモあり」と「メモなし」で答えが一致することを、
  追記を挟みながら確認する（`/refactor-safely` の等価検証にあたる）
- **並行読み**（レビューで追加）: 同一セッションの読みを 2 本／8 本同時に走らせ、全走査と一致し、
  追記分が二重に入らないこと。メモは共有物なので、コピーせず畳むとここが壊れる
- **本物の差し替え**（レビューで追加）: `unlink` してから**より大きい**ファイルを作る
  （inode 再利用の経路）
- **in-place の書き直し**（Codex で追加）: `unlink` せず `writeFile` で上書きし、旧 offset を
  超えて再成長させる。inode も birthtime も変わらないので、**stat 由来の指紋では必ず素通りする**
  — 実際、この 1 件が stat 版の実装で赤くなることを確認してから中身ベースへ移した
- **読みの途中の差し替え**（Codex で追加）: 差し替えを open の前後・3 箇所に置き、どこで起きても
  memo が汚染されないこと
- **先頭を保った置換**（CodeRabbit で追加）: 旧ファイルの先頭 3 行をバイト単位でそのまま持つ別ファイルに
  差し替える。先頭指紋では区別できず、単一 handle にして初めて緑になった
- **fold の最中の in-place 書き直し**（CodeRabbit で追加）: fold が EOF に達した read を掴んで
  同じ inode を書き換える。handle でも防げないので、境界 anchor の前後比較で捉える

## 測った

実ファイル（7.8MB / 31,667 行、`sessionPrompts` を 20 回）:

| | 初回（cold） | 2 回目以降（中央値） |
|---|---|---|
| 全走査（この PR の前） | 50ms | **毎回 50ms** |
| stat 版（途中の実装） | 51.7ms | 0.20ms |
| **anchor 版（採用）** | 49.4ms | **0.50ms** |

数字は 1 つ前の実装のもの。**単一 handle 版はまだ静かな機械で測り直せていない**（この開発機は
load average 73〜78 で、同一条件の A/B/A ですら 2.15ms → 40.31ms → 15.16ms とばらつく）。
1 回の refresh あたりの `open` は 4 回から 1 回に減っている。
